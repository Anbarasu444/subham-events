## Context
Vendors upload images/videos up to 30 MB; users upload event/profile media; invitations are generated assets. Media must be validated server-side, private by default, resized for low/mid-range devices and cheap to deliver (CLAUDE.md §23). The user will create the ImageKit.io account(s) and has asked that no Google Cloud Storage be created.

## Options considered
1. **ImageKit.io** — managed storage + CDN + real-time URL transformations (resize, format, quality, video thumbnails); private files with signed URLs; server-side SDK for Node.js; client upload with backend-generated auth parameters. No thumbnail pipeline to build.
2. Google Cloud Storage / Firebase Storage — rejected by the user.
3. AWS S3 / Cloudflare R2 — not chosen; would need a separate image-processing pipeline.

## Decision
Use **ImageKit.io** for all photos and videos:
- All uploads are **private files**; the backend issues **signed delivery URLs** (24 h TTL for public marketplace media, 15 min for private media) after authorization checks.
- Clients upload directly to ImageKit using **single-use upload auth parameters** (token, expire, signature) generated by the backend; folder, file name and privacy flag are fixed by the backend.
- The backend verifies every completed upload via the ImageKit API (path, size, type) before marking it `READY`; invalid files are deleted.
- Variants (thumb/medium/video poster) via URL transformations; no worker-side image processing.
- Separate ImageKit accounts (or environments/keys) for non-production and production; the **private key stays server-side** (`IMAGEKIT_PRIVATE_KEY`); public key and URL endpoint are public identifiers.
- Metadata (owner, status, `fileId`, size, type) lives in PostgreSQL; ImageKit is never the system of record.

Details: `architecture/media-and-deep-links.md`.

## Consequences
- Less backend work (no thumbnail/transcoding worker); image sizing and CDN come built in.
- Vendor lock-in to ImageKit URL transformation syntax — isolated in the backend `integrations/imagekit` adapter that builds URLs, so clients only receive ready URLs.
- Cost depends on ImageKit plan limits (storage, bandwidth, video processing); the user should check plan limits against expected vendor video volume.
- Taking a public file offline is bounded by the signed-URL TTL (≤ 24 h) unless the file is deleted/purged.

## Review trigger
ImageKit plan limits or cost reached; a need for media types ImageKit does not handle; M60 (Media / Storage Integration) and M65 (Security Audit).
